Set up the Azure SRE Agent and monitoring for your application

Dev and test only. Not a production pattern. Everything here was tried in sandbox subscriptions with synthetic data. A production application must follow the B.C. government Public Cloud Landing Zone rules and policies, and the production path may be quite different (identity, networking, data residency, support model). That path has not been explored yet. Plan it with the Public Cloud team before you copy anything here into production.

Written from two setups: ai-adoption-document-intelligence (an app that runs locally and on OpenShift) and digital-marketplace-next (an app that runs on Azure Container Apps). Items marked untested have not been run in either repository.

Azure SRE Agent investigates application health for you: it reads your telemetry, answers questions, reacts to alerts and runs scheduled checks. This guide shows how a team connects an application to it for a dev or test environment, and sets up alerting, including email.

What the agent does and does not do

It does

  • Query the Azure resources you give it (Log Analytics, Application Insights, Azure Monitor metrics and alerts, resource configuration) with its own managed identity.
  • Answer questions such as "why is this service failing?" and "what changed in the last hour?".
  • Pick up Azure Monitor alerts, open an investigation, and merge repeat firings of one alert rule into a single thread.
  • Run scheduled tasks, such as a daily health check, and send summaries by Outlook, Gmail, or Teams.
  • Propose mitigations based on the source code you give it. In Review mode, Azure write operations wait for an SRE Agent administrator.

It does not

  • Collect or ship logs. It reads what is already in Azure. An app that is not on Azure needs a shipper (Path A).
  • Create alerts. It reacts to alert rules you define; it does not watch your app on its own.
  • See anything you did not ship. If a line was filtered out or never logged, the agent cannot explain it.
  • Gate everything behind approval. Review mode only asks for approval on Azure infrastructure operations. Sending email or posting to Teams is not gated; use tool access policies or hooks if you need a checkpoint.

What it reads from application logs

Where the app runs What the agent can read
Outside Azure Only the columns of your custom table: whatever your shipper sends, typically a timestamp, service, level, status code and the log line itself.
Azure Container Apps Console and system logs in the workspace (ContainerAppConsoleLogs_CL, ContainerAppSystemLogs_CL), plus Application Insights requests, exceptions, dependencies and traces, and platform metrics.

The agent sends what it reads to a language model. Log lines can contain personal information, so keep user data, tokens and document content out of logs it can see, and confirm your Privacy Impact Assessment covers this flow.

Prerequisites and permissions

  • An Azure subscription in your Project Set and a resource group for monitoring resources.
  • Azure CLI, signed in with az login.
  • Network access to *.azuresre.ai and sre.azure.com.
  • An SRE Agent. Create one, or reuse a team agent; see Connect the application to the agent.
You need To do Notes
Owner, or Contributor plus User Access Administrator, on the resource group Create the agent and assign it roles A conditional User Access Administrator grant limited to the roles you assign is tighter.
Contributor on the monitoring resource group Create the workspace, Application Insights, alert rules, action group Path B pipelines need this at subscription scope if they create the resource group.
Monitoring Metrics Publisher on the data collection rule Ship logs (Path A) A workspace or resource-group grant returns 403.
An Entra app registration, if not using your own user Ship logs from a deployed environment (Path A) Not self-service; see Path A.
SRE Agent Administrator Approve the agent's proposed actions Only administrators can approve.

Agent creation gives the agent a user-assigned managed identity. The read roles it needs on your monitoring resource group are Reader, Monitoring Reader and Log Analytics Reader. Agent creation also assigns Monitoring Contributor at subscription scope so it can acknowledge and close alerts. Check what your agent holds before you rely on it.

Landing Zone checks

These can block a setup, so check them first. Raise a Public Cloud Service Request for any exception.

  • Region. The Landing Zone allows Canada Central and Canada East. Keep the workspace, collection endpoint, and your resources in Canada Central.
  • Public endpoints. Policy denies many public PaaS endpoints and plain-HTTP ingress. Path A needs to reach the collection endpoint from outside Azure.
  • Identity. App registrations and client secrets are exceptions, not defaults (Path A).

Path A: application outside Azure

Use this when the app runs locally, on OpenShift, or anywhere else Azure cannot see.

app logs ─> Fluent Bit ─> Data Collection Endpoint ─> Data Collection Rule ─> Log Analytics table
                                                                                  │
                                                                       SRE Agent queries it

Your existing pipeline (Loki, Splunk, OpenShift logging) stays as it is. Fluent Bit runs beside it and ships a filtered subset. This guide uses Fluent Bit; see Alternatives to Fluent Bit for other shippers.

Do not use the legacy HTTP Data Collector API. It was retired on 14 September 2026. It still may return HTTP 200 and create tables, but ingests nothing.

Step 1: Create the Azure side

Set variables:

RG=<monitoring-resource-group>
LOCATION=canadacentral
WORKSPACE=<workspace-name>
TABLE=MyApp_CL

Create a Azure Log Analytics Workspace (skip if you have one), a custom table, and a Data Collection Endpoint (DCE). Keep the schema small; the agent only needs enough to judge health.

az monitor log-analytics workspace create -g "$RG" -n "$WORKSPACE" -l "$LOCATION"

az monitor log-analytics workspace table create -g "$RG" --workspace-name "$WORKSPACE" -n "$TABLE" \
  --columns TimeGenerated=datetime Service=string Level=string StatusCode=int RawData=string

az monitor data-collection endpoint create -g "$RG" -n myapp-dce -l "$LOCATION" \
  --public-network-access Enabled

Public access on the DCE is the simplest option for dev and test. Whether the Landing Zone allows it, or needs a private path through an Azure Monitor Private Link Scope, is a question for the Public Cloud team. Record the DCE's Logs ingestion URI (logsIngestion.endpoint).

Create the Data Collection Rule (DCR). Save this as dcr.json, replacing the placeholders. The stream declaration must match, exactly, the fields Fluent Bit sends, and the stream must be named Custom-<table>. 

{
  "location": "canadacentral",
  "properties": {
    "dataCollectionEndpointId": "<DCE resource ID>",
    "streamDeclarations": {
      "Custom-MyApp_CL": {
        "columns": [
          { "name": "TimeGenerated", "type": "datetime" },
          { "name": "EventTime", "type": "string" },
          { "name": "Service", "type": "string" },
          { "name": "Level", "type": "string" },
          { "name": "StatusCode", "type": "int" },
          { "name": "RawData", "type": "string" }
        ]
      }
    },
    "destinations": {
      "logAnalytics": [{ "name": "la", "workspaceResourceId": "<workspace resource ID>" }]
    },
    "dataFlows": [
      {
        "streams": ["Custom-MyApp_CL"],
        "destinations": ["la"],
        "outputStream": "Custom-MyApp_CL",
        "transformKql": "source | extend _t = todatetime(EventTime) | extend TimeGenerated = iff(isnull(_t), TimeGenerated, _t) | project TimeGenerated, Service, Level, StatusCode, RawData"
      }
    ]
  }
}

az monitor data-collection rule create -g "$RG" -n myapp-dcr -l "$LOCATION" --rule-file dcr.json
DCR_ID=$(az monitor data-collection rule show -g "$RG" -n myapp-dcr --query immutableId -o tsv)
DCR_RES_ID=$(az monitor data-collection rule show -g "$RG" -n myapp-dcr --query id -o tsv)

The transform keeps the app's own timestamp when a line has one and falls back to Fluent Bit's read time otherwise. DCR transforms support only a subset of KQL: coalesce fails validation with InvalidTransformQuery, so the transform uses iff/isnull. Testing the converted value, not the raw string, also stops a malformed EventTime from producing a null timestamp and getting the record rejected.

Step 2: Choose the identity that writes logs

Situation Identity
Shipper runs on Azure compute (App Service, Container Apps, AKS, a VM) Managed identity. No registration needed.
Deployed or shared, outside Azure (for example OpenShift) Entra app registration and its service principal
One developer, trying it out locally Your own user, through a loopback token broker (below)

Whichever it is, grant Monitoring Metrics Publisher on the DCR itself. A workspace-scoped or resource-group-scoped grant is not enough and returns HTTP 403.

az role assignment create --assignee "<client ID, or your user's object ID>" \
  --role "Monitoring Metrics Publisher" --scope "$DCR_RES_ID"

For your own user, add --assignee-principal-type User and use az ad signed-in-user show --query id -o tsv for the object ID.

Requesting an app registration. Registrations in the B.C. government tenant are not self-service. Request one through My Service Centre and include:

  • A display name following <org>-<licenceplate>-<env>-<platform>-<system>-<purpose>-<auth>, for example citz-abc123-dev-azure-myapp-logs-secret.
  • The auth method and its justification. A client secret is an exception, so explain that Fluent Bit's Logs Ingestion output authenticates with a client ID and secret.
  • No API permissions. Access comes from the Azure role, not Graph scopes.
  • An owner group of at least two members, and a review date no more than 12 months away.

Secrets last 180 days at most, so plan rotation before you ship. Keep the secret in Azure Key Vault, or Vault for apps on OpenShift, and mount it into the Fluent Bit pod. Never commit it or put it in a shared .env.

Local prototyping with a token broker. If the registration is not approved yet, authenticate Fluent Bit as yourself, using the token broker script. A small loopback server runs az account get-access-token --resource https://monitor.azure.com and returns the token as an OAuth2 response; Fluent Bit's auth_url points at it instead of using a client secret. Three constraints make it work:

  • Fluent Bit 5.1 or newer. Earlier versions reject auth_url as an unknown property.
  • Host networking on the container. The plugin allows plain HTTP for auth_url only on a loopback address, so 127.0.0.1 has to mean the host.
  • An active az login session. Bind the broker to 127.0.0.1 only. When conditional access forces a new sign-in the broker fails and delivery pauses until you run az login; Fluent Bit buffers and retries in the meantime.

Local prototyping only. It ships logs under a personal identity and stops whenever your session expires. Never use it in a shared, deployed or unattended environment, and move to an app registration before anyone else relies on the data.

Step 3: Configure Fluent Bit

Tail the log files, filter with a Lua script, and send with the azure_logs_ingestion output. Putting each line in a RawData key lets the script map it onto the table columns. 

pipeline:
  inputs:
    - name: tail
      alias: myapp
      path: /var/log/app/*.log
      tag: app.myapp
      key: RawData
      db: /var/lib/fluent-bit/positions.db
      skip_long_lines: true
      storage.type: filesystem

  filters:
    - name: lua
      match: app.*
      script: /fluent-bit/etc/filters.lua
      call: keep_health_signal

  outputs:
    - name: azure_logs_ingestion
      match: app.*
      tenant_id: ${AZURE_LOGS_TENANT_ID}
      client_id: ${AZURE_LOGS_CLIENT_ID}
      client_secret: ${AZURE_LOGS_CLIENT_SECRET}
      dce_url: ${AZURE_LOGS_DCE_URL}
      dcr_id: ${AZURE_LOGS_DCR_ID}
      table_name: MyApp_CL
      time_key: TimeGenerated
      time_generated: true
      compress: true

With the token broker, replace the three credential lines with auth_url: http://127.0.0.1:8899/token (and placeholder client_id and client_secret values), and run the container with host networking. The working configuration shows the whole pipeline. Keep tail positions (db) on a persistent volume so a restart does not re-send history.

Filter hard. Log Analytics bills per GB, and the agent works better on signal than on noise. Keep your full stream in your primary pipeline for detailed debugging.

  • Keep warn and error lines, HTTP request records with a status of 400 or above, and unstructured lines that match failure patterns (Exception, ECONNREFUSED, EADDRINUSE).
  • Drop info and debug lines, successful requests, startup banners and hot-reload output.
  • Strip ANSI colour codes, and set Service, Level and StatusCode on each kept record. In Fluent Bit this is a short Lua function that matches on text and returns -1 to drop a record; filters.lua in ai-adoption-document-intelligence is a working example.

Two pitfalls from real use:

  • Keep narrow noise patterns, and test keep patterns first. A loose noise pattern ("ready in ") silently discarded real address already in use errors.
  • Do not treat a context field as an alert marker. A field such as alertType that also appears on routine lines must not force a line to be kept.

Step 4: Verify with a query

MyApp_CL
| where TimeGenerated > ago(1h)
| summarize count() by Service, Level

Rows arrive only once something logs a warn or error, so trigger one on purpose, such as a request to an unknown route. Confirm with a query, not a status code. An HTTP 204 from the ingestion API does not prove the rows are queryable. The first write to a new table took about seven minutes; re-query before assuming failure.

Common failures:

  • HTTP 403: Monitoring Metrics Publisher is not assigned on the DCR itself.
  • HTTP 404: wrong DCR immutable ID, or the stream is not named Custom-<table>.
  • HTTP 400 on every record: the stream declaration does not match the fields Fluent Bit sends.
  • unknown configuration property 'auth_url': Fluent Bit older than 5.1.
  • No rows and no errors: the filter dropped everything. Temporarily switch the output to stdout with format: json_lines to see what is sent.

Alternatives to Fluent Bit

Fluent Bit was chosen because it was already in the toolchain next to Promtail, and its azure_logs_ingestion output speaks the supported Logs Ingestion API. Others exist; none of these were tried in either repository.

Option Where it fits Watch for
Azure Monitor Agent (custom text logs, configured by a DCR) Apps on Azure VMs or Arc-enabled servers Needs an Azure or Arc machine, so it does not suit containers on OpenShift or a laptop. No scripting for filtering; filter in the DCR transform.
OpenTelemetry Collector with the Azure Monitor exporter Apps already emitting OpenTelemetry Writes to Application Insights (a connection string), not a custom table. The agent then reads the traces, exceptions and requests tables, as in Path B. This will not give the agent access to frontend and backend logs, however, so another solution like Fluent Bit is needed. Confirm your policy allows connection-string ingestion.
Instrument the app directly with the Azure Monitor OpenTelemetry distro, or the azure-monitor-ingestion SDK You control the code and want no extra container Couples the app to Azure and sends from the app process. The same identity and DCR rules apply to the SDK.
Logstash with the Microsoft Sentinel output plugin Teams already running Logstash Heavier than Fluent Bit. Check the plugin version uses a DCR.
Vector, Fluentd, or older Log Analytics plugins Teams already running them Many use the retired Data Collector API and now ingest nothing. Confirm the sink calls the Logs Ingestion API before choosing one.

Whatever you choose, the Azure side (workspace, DCE, DCR, role on the DCR) and the "filter hard" guidance stay the same, and you still verify with a query.

Path B: Azure-native application

Use this when the app runs on Azure (here, Container Apps). Azure already collects most of what the agent needs, so there is no shipper and no log-writing identity. The digital-marketplace-next repository holds the working Bicep in infra/azure/ and the decision record 0069.

  1. A workspace and a workspace-based Application Insights resource (modules/monitoring.bicep). Give the environment its own workspace so its data stays apart from the agent's own.

  2. Send platform logs to the workspace. Set the Container Apps environment's appLogsConfiguration to log-analytics (modules/environment.bicep). Console output then lands in the workspace with no agent or sidecar.

  3. Send application telemetry to Application Insights. The Node backend loads @azure/monitor-opentelemetry first and starts it only if APPLICATIONINSIGHTS_CONNECTION_STRING is set (telemetry.ts). Pass the connection string to the container as a secret and set OTEL_SERVICE_NAME (modules/apps.bicep). Other runtimes have an equivalent Azure Monitor OpenTelemetry distro.

  4. Expose a health endpoint (if desired) (/status) for both container probes and an availability test.

  5. Define alert rules (if desired) (modules/alerts.bicep):

    Rule Type Fires when
    status-down Availability test, severity 1 /status fails from two test locations
    5xx Container Apps metric, severity 2 More than five 5xx responses in 15 minutes

  6. Grant the agent read-only roles on the resource group (modules/agent-access.bicep): Reader, Monitoring Reader and Log Analytics Reader. The Digital Marketplace pipeline then adds the group to the agent's managed resources; see the next section.

  7. Deploy through a pipeline with no stored credential. The workflow deploy-azure.yml signs in with GitHub OIDC as a user-assigned managed identity, so nothing needs an app registration. The one-time bootstrap is documented in infra/azure/README.md because it needs rights the pipeline does not have.

Connect the application to the agent

Common to both paths.

  1. Create or reuse the agent at aka.ms/sreagent/portal. A shared team agent works; each application's resource group is attached to it. Choose the Reader permission level if you do not want the agent to make any changes, and leave the run mode at Review.

  2. Attach the resource group that holds your workspace and alert rules: in the portal, Choose resource groups, or through the agent's API, which the Path B pipeline does: 

    url="https://management.azure.com${SRE_AGENT_ID}?api-version=2026-01-01"
agent=$(az rest --method get --url "$url")
# The API rejects a managed-resources change that does not repeat the identity.
body=$(jq -c --arg rg "$RG_ID" '.properties.knowledgeGraphConfiguration as $kg
  | {properties:{knowledgeGraphConfiguration:{identity:$kg.identity,
      managedResources:((($kg.managedResources // []) + [$rg]) | unique)}}}' <<< "$agent")
az rest --method patch --url "$url" --body "$body"

    The call is asynchronous; poll properties.provisioningState until it leaves InProgress.

  3. Give the agent context with source code or knowledge files. If desired, give access to your Github or Gitlab repos or project knowledge for better diagnostic analysis and suggestions.

  4. Confirm the agent can read the resources. Ask it to list the resources in the group and to query your workspace. If a query fails, assign Log Analytics Reader on the workspace.

  5. If needed, describe your data. Path A: name the custom table, list its columns, and say what each Service and Level value means. Path B: say which Application Insights resource and which Container App is the backend.

  6. Start with questions, then automate:

    • "Summarise errors over the last 24 hours by service."
    • "Which endpoints returned 5xx most often today?"
    • "Can you set up a scheduled health check that runs every morning at 8am PCT?"

  7. Set the run mode on every response plan and scheduled task. The agent's own default is Review, but a new response plan or scheduled task defaults to Autonomous. Pick Review explicitly until you trust the behaviour, and keep Autonomous for non-production only.

Alerting and email notifications

You can add Gmail, Office 365 Outlook, and Microsoft Teams connections through the Build + Setup > Extensions > Connectors > Add Connector > Notifications. These require signing in to the respective accounts and granting permissions to the agent. This allows the agent to read and send messages after performing scheduled tasks.

What triggers the agent

  • Azure Monitor alerts. In the agent portal, Builder > Incident platform (On the new interface: Build + Setup > Extensions > Connectors), connect Azure Monitor and authenticate with the agent's managed identity. The agent checks for new alerts every minute and opens an investigation. Incident response plans choose which severities it takes and the run mode. Path B's two alert rules qualify as they are. (Connection untested here.)
  • Scheduled tasks. These can be created and customized through the chat interface to do health checks or other tasks on specific resources/tables or a more wholistic approach. If the SRE agent is connected to an email/notification service, it can also send results of the scheduled tasks through that channel.

Lessons learned

Both setups

  • Confirm data arrives in the logs with a query, not a status code. The retired Data Collector API returned 200 while storing nothing. Ingestion acknowledgement is not proof.

From the document-intelligence setup (Path A)

  • The grant on the DCR matters. A workspace-scoped Monitoring Metrics Publisher gives 403.
  • Fluent Bit 4.x and 5.0 reject auth_url. Use 5.1 or newer, with host networking, or use an app registration.
  • Missing logs were often missing log statements. Nest rejected unknown routes and 401/403s before the request logger ran, so those requests left no line. A small exception filter that logs them at warn fixed the gap.
  • Filter rules decay. An alertType field is not an alert marker (it also appears on routine lines), and a loose noise pattern ("ready in ") dropped real address already in use errors. Test keep patterns before noise patterns.
  • Two log views will disagree by design: the pipeline keeps everything, Azure keeps a subset. Document where the filter rules live.
  • Azure Data Explorer was evaluated as a destination and rejected: it still needs an app registration and adds an always-on cluster.

From the digital-marketplace setup (Path B)

  • Use a user-assigned managed identity with a federated GitHub credential for the pipeline. No app registration, no secret.
  • Scope the pipeline's role grants. A conditional User Access Administrator limited to the three read roles lets the pipeline wire up the agent but nothing else.
  • Landing Zone policy denied plain-HTTP ingress, so a separate backend app was impossible. The backend runs beside the web server in one app and is reached on localhost.
  • Deploy in two passes when an image needs a value that depends on the environment's domain.
  • The agent API is fussy. A managed-resources change must also name the agent's identity, and the update is asynchronous.
  • Alert rules without a notification target are quiet. Add the action group when you add the rules.
  • Contributor on the agent also lets the pipeline change its mode. A custom role limited to Microsoft.App/agents/write would be tighter. Updating managed resources with the pipeline's identity is untested on the agent's own identity; if it fails authorisation, also grant Managed Identity Operator on that identity.
  • Availability tests probe from US locations, which is fine for a synthetic, public dev environment and a question to raise for anything else.

Before you go to production

These are open and need exploration with the Public Cloud team:

  • Private connectivity: a private Azure Monitor path for log ingestion, and private reach to your app, in place of public endpoints.
  • A production identity model (managed identity or workload identity, rotation, owner groups).
  • Production run mode, tool access policies and who holds SRE Agent Administrator.
  • Log content rules and the Privacy Impact Assessment for what the agent may read.
  • Cost: Log Analytics ingestion per GB and agent usage billed in Azure Agent Units.
  • Alert routing and on-call: who is paged, through what, and how the agent's summaries fit.
