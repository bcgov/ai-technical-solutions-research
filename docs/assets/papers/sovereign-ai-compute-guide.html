1. Purpose

This document helps platform teams and project owners understand how to run AI workloads on BC Government's sovereign compute infrastructure. It covers:

  • How to request resources — what your application needs, why, and how to make a namespace request that the platform team can act on
  • What tools are available — as the OpenShift AI Hub is upgraded with tools like vLLM, KServe, LLM Compressor, InstructLab, lm-eval, and Feast, this document helps teams navigate these tools without being overwhelmed
  • How to utilize all available compute — GPUs, CPUs with AMX acceleration, memory, and network — for the best utilization across all workloads
  • How platform teams can support allocation — from oversubscription to underutilization, guiding resource allocation based on actual workload needs
Why this document exists: Our current AI Hub has evolved from dual-socket 2nd-generation Xeon, to 5th-generation Xeon, and is now upgrading to dual-socket Xeon 6 with GPU acceleration. Through each upgrade, not all teams and projects fully utilized the resources available. The question is: if we provision these new resources, can teams actually use them? If there is underutilization, can teams that need more compute get more? Can we do distributed computing to combine more memory, more GPUs, more CPUs — and what would that look like? This report helps guide those decisions.
Practical output: This report is intended to help platform teams and application teams translate AI use cases into schedulable workload shapes. Before a project requests "AI compute" or "a GPU," the workload should be described by model size, precision, context length, concurrency, latency target, data movement, storage growth, CPU/RAM needs, GPU/MIG needs, and operational ownership. Platform teams can then map the request to a CPU-only profile, MIG slice, full GPU, full node, or future multi-node pattern. Application teams can use the same framework to ask better questions before designing an architecture around a tool or model.

A Practical Example: What Does a GPU Partition Actually Support?

To illustrate why this guide matters, consider the GPU resources alone:

We have 6× RTX Pro 6000 GPUs, each with 96 GB VRAM. With NVIDIA MIG (Multi-Instance GPU), each GPU can be partitioned into up to 4 isolated slices — that is 4 different projects running on 1 GPU. Across the cluster, that means a maximum of 24 GPU slots (6 GPUs × 4 partitions). But each partition only gets 96 GB ÷ 4 = 24 GB VRAM.

Is 24 GB enough? That depends entirely on your application context:

QuestionWhy It MattersExample Impact on 24 GB MIG Slice
What is your application? A single-user chat demo has different needs than a batch document processor or an agentic workflow A demo fits easily. A production service serving a ministry does not — it needs concurrency headroom.
How many concurrent users? Each concurrent user grows the KV-cache. Government services do not serve 1 user. A 7B Q4 model uses ~5 GB for weights. At 4 concurrent users with 8K context: +2 GB KV-cache (7 GB total, fits). At 16 users: +8 GB (13 GB, fits). At 32 users with 16K context: +32 GB (exceeds 24 GB — OOM).
What context length do you need? Short Q&A (2K–4K tokens) vs. long document processing (16K–32K) vs. agentic workflows (32K–128K) have very different memory profiles At 32K context, KV-cache per user is 4× larger than at 8K. An agentic workflow requiring 64K+ context may not fit even a single user alongside model weights in a 24 GB slice.
Is this for real-time serving or batch? Batch processing can queue requests sequentially (low concurrency, high throughput over time). Real-time serving must handle bursts. Batch: 1–2 concurrent requests, KV-cache stays small — 24 GB works well. Real-time burst of 20 users: KV-cache spike, potential OOM.
Will your workload grow? A model serving 4 users today may need to serve 40 after onboarding more teams. KV-cache grows linearly. What fits today at 4 users may OOM at 20. The namespace request should account for projected growth, not just day-one load.
Is this inference, fine-tuning, or evaluation? Training requires optimizer states + gradients (2–4× model weight size). Evaluation may not need a local GPU at all. Fine-tuning a 7B model with LoRA needs ~15–20 GB (weights + adapters + gradients) — a 24 GB MIG slice is tight. QLoRA of a larger model does not fit.
The point: "Can my model fit?" is the wrong first question. The right questions are: What is my application? How many users? What context length? Real-time or batch? Will it grow? Those answers determine whether a MIG slice, a full GPU, multiple GPUs, or CPU-only compute is the right fit. This document helps you work through those questions.

2. Key Terms

This document uses terms from distributed systems, GPU computing, and AI infrastructure. Here is what they mean in plain language:

Heterogeneous ComputingUsing different types of processors together — CPUs, GPUs, and specialized accelerators — each handling the work they do best, rather than relying on one type alone.Our platform has both Xeon 6 CPUs (with AMX matrix acceleration) and RTX Pro 6000 GPUs. Using both together serves more projects at lower cost than GPUs alone.

NUMA (Non-Uniform Memory Access)In a dual-socket server, each CPU socket has its own local memory. Accessing memory on the other socket is slower. NUMA-aware scheduling places workloads close to their memory.Scheduling an AI workload on the wrong socket can reduce throughput. Platform teams use NUMA-aware placement to ensure workloads run efficiently.
Tensor ParallelismSplitting a single model across multiple GPUs so each GPU holds part of the model and they compute together in parallel.When a model is too large for 1 GPU, tensor parallelism lets it run on 2 or more. Requires high-bandwidth connection between GPUs.
KV-Cache OffloadMoving KV-cache data from GPU VRAM to CPU RAM when GPU memory runs low. Trades some latency for the ability to serve more concurrent users.With 2 TB of CPU RAM per server, KV-cache offload can dramatically increase the number of concurrent users a GPU model can serve.
Sovereign ComputeComputing infrastructure owned and operated by the government, where data stays within government-controlled systems and never leaves to third-party cloud providers.All AI workloads described in this guide run on BC Gov's own hardware in government data centers — no data leaves sovereign infrastructure.

2.2 What This Compute Can Do — The Utilization Challenge

This is a powerful platform. With 144 cores, 288 MB LLC, ~800 GB/s aggregate memory bandwidth (DDR5-6400 × 8 channels × 2 sockets per server × 3 servers), 6 TB RAM, and 6 GPUs with 576 GB VRAM — the question is not whether we have enough compute. The question is whether teams are actually utilizing it.

Historically, our AI Hub evolved from dual-socket 2nd-gen Xeon to 5th-gen Xeon, and not all projects fully utilized the resources available at each stage. The challenge with this upgrade is the same:

  • Are teams aware of what is available? CPU+AMX acceleration, GPU inference, large memory pools, and high-bandwidth networking are all available — but only useful if teams know how to request and configure them.
  • Are allocated resources being used? A namespace allocated 32 cores and 64 GB RAM but only using 4 cores and 8 GB wastes capacity that other projects could use.
  • Can underutilized capacity be shared? If a GPU sits idle 80% of the day, can another project burst onto it? If training runs overnight, can inference reclaim those resources during the day?
  • Can teams that need more get more? Distributed computing can combine GPUs, CPUs, and memory across servers — but the namespace and scheduling must be configured to enable it.

The compute tiers in Section 2.1 show what is available per server. The profiles in Section 4 help teams request what they actually need. The scheduling policies in Section 6 help the platform team ensure that idle resources flow to teams that can use them.

3. How Workload Math Determines Resource Requests

When a project requests resources, the platform team needs to understand what the application actually requires — not just "give me a GPU" or "give me 32 cores." The math below helps both sides speak the same language.

3.1 GPU Memory: Model Weights + KV-Cache + Concurrency

GPU memory is shared between the model weights (fixed cost) and the KV-cache (variable cost that grows with users and context length):

GPU memory used = Model weights + KV-cache (per user × concurrent users) + Framework overhead Example: Llama-3.1-70B, 8K context, FP16 KV-cache KV-cache per request = 2 × 80 layers × 8 kv_heads × 128 head_dim × 8192 context × 2 bytes ≈ 2.6 GB Scenario A — Low concurrency (batch processing, 4 users): Weights (Q4): ~35 GB + KV-cache: ~10 GB = ~45 GB → fits on 1 GPU (96 GB) Scenario B — Medium concurrency (production service, 16 users): Weights (Q4): ~35 GB + KV-cache: ~42 GB = ~77 GB → fits on 1 GPU, but limited headroom Scenario C — High concurrency (ministry-wide service, 32 users): Weights (Q4): ~35 GB + KV-cache: ~84 GB = ~119 GB → exceeds 1 GPU, needs 2 GPUs or KV-cache offload to CPU RAM

This is why the same model can work for a pilot (4 users) but needs a different profile for production (32 users). The profiles in Section 4 account for this.

3.2 CPU Compute: Active AI Participants, Not Just GPU Hosts

Modern CPUs are not bystanders in AI inference. The Xeon 6527P with AMX (BF16/INT8 matrix acceleration), AVX-512, and ~400 GB/s memory bandwidth per socket is a compute-capable AI accelerator in its own right. This is not theoretical — recent research and industry direction confirm it:

Heterogeneous EPD Disaggregation (Intel + SGLang/LMSYS, June 2026): Offloading vision encoding to Xeon 6 CPUs (AMX) while GPUs handle language model decode achieved ~1.2–1.3× request throughput improvement and ~1.3–30× P99 TPOT (time per output token) reduction over pure GPU EPD. The CPU resources are effectively "free" — they exist in every server regardless. Using them for appropriate inference stages improves platform utilization without additional hardware cost.
Arm AGI CPU (Arm, 2026): Arm has released its first production silicon designed specifically for agentic AI workloads — 136 Neoverse V3 cores, 2 MB L2 cache per core, DDR5-8800 support, and PCIe Gen6. This signals that the industry recognizes CPUs as first-class AI processors, not just GPU hosts. The compute direction is heterogeneous: CPUs and GPUs working together, each handling the stages where they are most efficient.

What CPU compute enables on this platform:

CPU WorkloadHow It WorksWhy It Matters for Utilization

The key insight from the LMSYS research: the device-aware weighted router dynamically balances work between CPU and GPU pools based on actual load. When CPUs are underutilized relative to their capacity, the router sends encoding work to CPUs. When GPUs are under pressure, CPUs absorb overflow. This is the operational model that maximizes utilization of all compute — and it is directly applicable to our Xeon 6527P + RTX Pro 6000 configuration.

Utilization, not hierarchy: The question is not "GPU for real work, CPU for leftovers." The question is: which stage of your AI pipeline benefits most from which compute tier? Encoding → CPU (AMX). Decode → GPU. Embedding → CPU. Training gradients → GPU. Optimizer states → CPU RAM. Orchestration → CPU. When all tiers are utilized for the stages they handle best, the platform serves more projects, more efficiently, at lower power cost.

7. AI Workload Boundary for GPU-Enabled Hosts

GPU-enabled hosts should be reserved for AI workload execution and tightly coupled AI platform services. This keeps expensive GPU, CPU+AMX, memory, PCIe, and network capacity available for workloads that actually need AI compute locality. General application hosting should continue to use standard OpenShift or application hosting patterns unless there is a documented workload-sizing reason to co-locate with AI compute.

Boundary principle: An AI workload is compute, data, model, evaluation, or orchestration work that directly supports AI/ML training, fine-tuning, inference, evaluation, retrieval, simulation, model serving, or model-quality operations. "AI-adjacent" application code should not automatically qualify for GPU-enabled host placement.
Allowed By DefaultWhy It Belongs On AI Compute

VLM, OCR, ASR, document intelligence, and batch scoringAI processing workloads where throughput, latency, model size, or data locality affect compute placement.
Embeddings, retrieval indexing, and vectorization jobsOften CPU/GPU/memory intensive and directly supports RAG, search, or grounding workloads.
Training, fine-tuning, LoRA/QLoRA, simulation, forecasting, and geospatial MLConsumes accelerator, CPU, memory, storage, and scheduling capacity as part of model development or AI analysis.

AI notebooks and workbenchesAllowed for AI/ML experimentation, benchmark development, workload profiling, and platform validation.

Ordinary relational databases or application state storesDatabases should use normal managed database or application hosting patterns unless there is a specific AI data-locality requirement.
Project management tools, admin portals, and non-AI business applicationsThese consume capacity without improving AI workload execution.
Practical rule: An API that directly serves a model, launches AI jobs, manages model/runtime execution, or performs AI pipeline stages may belong near AI compute. An API that only manages users, forms, settings, dashboards, or general workflow state should run on standard application infrastructure. A lightweight UI for an AI demo may be useful, but the UI itself should not consume GPU-enabled host capacity unless a documented technical reason exists.

This boundary matters for licensing and operations. If GPU-enabled hosts are licensed or operated as AI-only hosts, the platform needs a defensible definition of what counts as AI work. Without that definition, any application can be described as AI-adjacent and the cluster can slowly become general-purpose hosting with expensive accelerators attached.

8. Dynamic Workload Sizing, Queues, and Burst Utilization

AI workloads are often bursty, experimental, batch-oriented, or time-boxed. A static namespace allocation model can leave expensive GPU, CPU, memory, and network capacity idle. A better operating model is to define guaranteed baseline allocations, then allow approved AI workloads to temporarily use more capacity when the cluster is underutilized.

Dynamic sizing principle: if the cluster is quiet, approved workloads should be able to burst into unused CPU, GPU, MIG, memory, or distributed capacity to finish faster. If the cluster is busy, workloads should fall back to their guaranteed quota, queue, or follow priority and pre-emption rules. This requires licensing, host eligibility, scheduling policy, quota rules, and monitoring to agree with each other.

Dynamic sizing is different from traditional web application hosting. Web workloads are often sized for steady-state service capacity and horizontal scaling. AI workloads may need temporary access to large compute windows: a training run overnight, a document batch over a weekend, a benchmark sweep, a simulation burst, or an evaluation job that can wait behind production inference.

11. Recommendation

  1. Adopt the 5-profile system (A–E) with NUMA affinity and bandwidth pressure as first-class sizing dimensions — not just GPU/CPU/RAM counts.
  2. Start with Scenario 1 (conservative) to validate the platform topology, then graduate to Scenario 2 once contention characteristics are measured.
  3. Default new projects to Profile E (CPU-only). GPU allocation requires workload math: model size × precision × concurrency × context length, not "we need GPUs."
  4. Schedule by NUMA domain, not by node. The scheduling unit is the socket+memory+PCIe complex, not the server. Two bandwidth-heavy workloads on the same socket degrade each other regardless of core count.
  5. Quantize aggressively. LLM Compressor (Q4/Q5) changes the bottleneck from VRAM capacity to KV-cache bandwidth — understand both before approving a namespace.
  6. Measure before expanding. Before adding workloads beyond Scenario 1, measure actual memory bandwidth utilization, LLC miss rates, and PCIe throughput per namespace. The numbers in this document are estimated from hardware specs — operational data will refine them.
Bottom line: This is a heterogeneous compute platform — 6 GPUs, 6 NUMA domains (144 MB LLC each), 6 TB DRAM (~1.8 TB/s aggregate bandwidth), and 200 Gbps fabric. Every tier is finite. Namespace sizing must respect cache locality, memory bandwidth, NUMA topology, and PCIe placement — not just GPU count. The bottleneck shifts by workload stage; the profiles and placement policies in this document are designed to keep every tier productive without starving co-tenants.
